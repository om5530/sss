# SaaS foundation: current inventory

This is a source-code inventory for planning tenant boundaries. The legacy app is single-store: its business records have no tenant key, storefront tenant resolution is absent, and the admin role is global. New foundation Bakery/Membership models do not change these legacy boundaries. A foundation pass can establish tenant context and begin scoped core paths, but it does **not** make the application fully tenant-isolated. Do not onboard a second bakery until every route, write path, background/payment callback, index, and test has been audited for isolation.

## MongoDB collections

Model names below are the Mongoose names (and therefore the default collection names are their pluralized forms). `server/src/models/BakeryOperations.js` dynamically registers nine models and must be included in any model registry or migration inventory.

| Scope | Models / collections | Notes |
|---|---|---|
| Core tenant data | `Product`, `Category`, `Order`, `Coupon`, `Review`, `CakeRequest`, `ContactMessage`, `Payment`, `EventPlan`, `AuditLog` | Storefront, sales, support and audit records. All are currently unscoped. Reviews must scope through both product and customer; payments and audit records need the same tenant as their parent/action. |
| Core bakery operations | `BakeryMaterial`, `BakeryRecipe`, `BakeryProduction`, `BakeryWaste`; generated by `BakeryOperations.js`: `BakerySupplier`, `BakeryPurchaseFormat`, `BakeryPrice`, `BakeryRevision`, `BakerySheet`, `BakeryMovement`, `BakeryPurchase`, `BakeryReceipt`, `BakeryMigration` | Internal costing, purchasing, inventory and production. These are heavily cross-linked and contain nested snapshots/lines. They still need an explicit tenant decision before SaaS use; excluding them from an initial plan does not make their routes safe. |
| Identity / tenant-aware identity | `User`, `AdminSession`, `Otp` | Today customers and admin users share one global identity namespace. Customer identity should become bakery-scoped per the plan; platform staff identity and tenant staff membership/roles should be modeled separately. OTP challenges and admin sessions must bind to tenant or platform context as appropriate. |
| Global/platform candidates | `Counter` | Currently a global order-number sequence (`_id: "order-number"`). Decide whether IDs are tenant-local or globally unique; if local, key counter by tenant. `StoreSettings` is a global singleton today, but should become one document per tenant (tenant settings), leaving only true platform defaults global. |
| Singleton tenant configuration | `StoreSettings` | Fixed `_id: "store"`; holds tax, delivery, opening hours, contact details and UPI recipients. Convert to a tenant-keyed record. Never use platform-global defaults for tenant pricing/payment details after tenant resolution. |

## API surface and isolation priority

Routes mount in `server/src/routes/index.js` under `/api`. Core means required for the first tenant storefront; deferred means can be disabled or excluded from the first tenant offering, but must remain inaccessible cross-tenant if enabled. “Public” describes caller access, not shared data: public storefront requests still require host-to-tenant resolution.

| Route group | Classification | Tenant boundary / action |
|---|---|---|
| `GET /health`, `GET /shop` | Global + public | Health is platform-wide. `/shop` reads the singleton settings and must resolve tenant from host before it returns tenant hours/config. |
| `/products` (menu, category, product, reviews) | Core + public | Resolve tenant from host on every request. Scope product/category/review queries and review purchase eligibility. Current menu/category aggregation and slug lookups are global. |
| `/cart/price` | Core + public | Scope product, recipe-cost and coupon reads to resolved tenant; current endpoint accepts arbitrary product IDs and uses globally matched data. |
| `/orders` | Core + public/customer | Scope creation, guest-order ID access, customer history, lifecycle and stock/coupon effects. Current `GET /:id` finds globally and allows any holder of a guest order ID; admin bypasses account ownership globally. |
| `/payments` and `POST /payments/webhook`, `/payments/razorpay-webhook` | Core + public callbacks | Resolve payment/order to tenant from durable provider reference, verify signature, and scope every update to that tenant. Webhooks cannot rely on an interactive host session. |
| `/auth` | Core + public/customer | Login/OTP/social account lookup is globally keyed by phone/email/provider ID; define tenant-aware customer identity and a separate platform/admin identity path. |
| `/contact`, `/cake-requests`, alias `/custom-requests` | Core + public | Public submission and admin triage must store and filter by resolved tenant. The alias mounts the same handler. |
| `/admin/*` | Core tenant-admin | Existing `requireAuth` + `requireRole('admin')` checks only global role. Every query, mutation, export, report and related lookup needs tenant membership and tenant scope; ID-based reads need parent-tenant checks. |
| `/admin/bakery/*` | Core tenant-admin; optional reports deferred | Same global admin gate; includes materials, recipes, inventory, production, purchasing, receipts, waste and reports. Keep disabled for tenants without the feature, and scope all linked models before enabling. |

The current **More tools** admin menu links to `/admin/dashboard`, `/admin/bakery/dashboard`, `/admin/prep`, `/admin/categories`, `/admin/customers`, `/admin/cake-requests`, `/admin/activity`, `/admin/qr`, `/admin/reports`, `/admin/coupons`, and `/admin/enquiries`. Bakery pages are also reachable at `/admin/bakery/{dashboard,production,reports,migration,purchasing,calculator,recipes,product-mapping,materials,inventory,waste}`. The “Live queue” link is commented out; `/admin/queue` redirects to orders. `/admin/settings` is outside the dropdown. These frontend routes are not security boundaries; API middleware and data scope are.

## Isolation hazards to address

- **Unscoped reads/writes are pervasive.** Public product/menu/category lookups, coupon resolution and admin lists/reports query collections without a tenant predicate. Admin queries include broad `find()`/`countDocuments()`, ID-only `findById()`, and bulk updates such as stock reset and category/product mapping. Bakery context helpers load all materials, recipes, suppliers, formats, prices and scheduled sheets. A Mongoose query plugin alone is insufficient for aggregates, raw updates, `findById`, population, webhook handlers and cross-model service calls; make tenant context explicit and test each path.
- **Global role and identity.** `requireRole('admin')` authorizes any admin for all stores. Users are uniquely keyed by sparse global email/phone indexes and provider IDs are global; auth flows search by phone/email/Google/Firebase identity. Add tenant membership/role authorization and decide how account linking works without letting the same phone silently cross customer data boundaries.
- **Unique indexes need tenant prefixes.** Existing unique constraints include product `slug`, category `(group,nameKey)`, coupon `code`, order `orderNumber`, event `eventKey`, generated sheet `code`, generated purchase `code`, receipt `operationKey`, revision `(recipeId,version)`, recipe `productId` (partial unique), review `(product,user)`, plus sparse unique user email/phone. Any tenant-local values need `{tenantId, ...currentKey}` indexes and a migration that resolves collisions before constraints change. Supplier codes/material codes and operation keys also need an explicit uniqueness scope.
- **Singleton and counters.** Settings use the fixed `store` document; counters increment one global order-number document and emit a store-branded prefix. Define global-vs-tenant identifiers, idempotency keys and references before moving to shared tenant collections.
- **Payment rails and callbacks.** Payment records link to orders but contain provider identifiers without tenant identity. Stripe and Razorpay webhooks are registered before JSON parsing and must continue receiving raw bodies; callback lookup must map provider IDs to a tenant safely, validate the signature, and update only that tenant’s order/payment. BYO credentials require tenant-specific key selection and webhook-secret rotation. Cash/manual settlement, UPI recipients and refunds are also tenant-specific.
- **Storage and external identities.** Product/cake images fall back to local filesystem storage when Cloudinary is absent; serverless local disk is ephemeral. Cloudinary uploads use fixed `sss` / controller-selected folders rather than tenant namespaces. Move to durable storage and tenant-specific folders/ownership checks. Firebase/Google identities and OTP issuance/verification are presently global; notifications, rate limits and any future messaging sender identities also need a tenant boundary. Current rate limiting uses in-memory state, which is per-process and unsuitable for shared tenant-wide quotas.
- **Background/in-process state.** Review serialization is an in-memory map keyed only by product ID; event stock, order stock, category migration, recipe pricing and bakery transaction services coordinate multiple records without tenant predicates. Tenant must be carried through the complete transaction and cache/idempotency keys.

## Dependencies and production configuration

Foundation dependencies are MongoDB/Mongoose (tenant-aware indexes and query paths), a trusted host/domain-to-tenant resolver, explicit tenant membership/auth, shared durable rate limiting/cache for quotas and host lookup, and durable object storage. Payments need per-tenant Razorpay/Stripe credentials plus signed webhook routing; auth currently depends on JWT, optional Google OAuth, Firebase phone auth and mock OTP. The deployment entry points are Express (`server/src/server.js`) and Vercel (`api/index.js`); both call the production-config guard.

Source review also found production-readiness concerns to carry into launch checks: mock OTP exposure is hard-coded on in `env.js`; the boot guard blocks it only when live payment keys are present, so production can still run with disclosed mock OTPs. `/auth/phone-config` reports `mode: 'mock'` unconditionally despite Firebase config values. Firebase web client defaults are embedded in source (client configuration, not server credentials); replace bakery-specific defaults with deployment/tenant config. Local-disk image fallback is not durable on serverless. The boot guard checks JWT length/default, Mongo URI, payment key pairs/webhook secrets, and localhost client URL, but does not require a real OTP provider or durable upload provider. Treat these as existing configuration gaps, not tenant-isolation controls; no deployment environment or secret values were inspected.
